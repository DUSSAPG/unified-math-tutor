# Content Completion Audit

Status: audit only, per instruction — **no fixes were made in this pass**.
Every item below is a finding, not a change. Scope: `TODO`, `FIXME`,
placeholder content, "coming soon" states, empty/dummy data, hardcoded
text bypassing localisation, missing assets, missing localisation,
broken routes, unused widgets, and deprecated code, across `lib/`,
`test/`, `assets/`, and `docs/`.

Severity follows this app's own existing release-blocker definition in
`docs/RC1_FEATURE_FREEZE.md` §6 (crash/dead-data/dead-end/accessibility/
localisation-leak = release-blocking) extended down to Low for pure
hygiene items with no user-facing effect.

## Critical

None found. No crash risk, data-loss risk, dead-end, or user-reachable
broken state was found anywhere in this audit.

Every one of these files exists, compiles, and is **never imported or
routed anywhere in `lib/`** — confirmed dead code, not reachable by any
user action:

|---|---|---|
| `lib/screens/admin_console_screen.dart` | `AdminConsoleScreen` | `Text('Admin Console Screen')` |
| `lib/screens/results/growth_screen.dart` | `GrowthScreen` | `Text('Growth Screen')` |

| `lib/screens/welcome/welcome_screen.dart` | `WelcomeScreen` | empty `SizedBox()` |

Origin: `lib/routes/route_suggestions.dart`, a leftover conversion-tool
file (its own comment: `// Route suggestions generated by converter`)
listing these plus references to classes that no longer exist at all
(`TutorBotModal`, `PaywallScreen`, `ResultsScreen`, `generateQuestions`,

the "No route registered" notes in
`docs/design_reference/SCREEN_TO_WIDGET_MAP.md`.

**Risk**: none to end users (unreachable). Real risk is to future
maintainers — a `HomeShell` class that isn't the real, wired one
(`lib/screens/home/home_shell.dart`), or a `WelcomeScreen` that isn't the
real, parameterized one (`lib/features/welcome/welcome_screen.dart`), is
exactly the kind of thing that causes an accidental wrong import later.

**Effort estimate**: Small (S) — delete 8 files + `route_suggestions.dart`
+ the stale `SCREEN_TO_WIDGET_MAP.md` "No route registered" rows once
confirmed genuinely obsolete; no route or navigation change needed since
nothing points at them.

### H2. Duplicate class names risk a wrong import

Two class-name collisions exist between real, wired code and the dead
stubs from H1:

- `WelcomeScreen`: real at `lib/features/welcome/welcome_screen.dart`
  (parameterized, in use) vs. dead at `lib/screens/welcome/welcome_screen.dart`
  (empty stub).
- `HomeShell`: real at `lib/screens/home/home_shell.dart` (the actual
  bottom-nav shell) vs. dead at `lib/screens/home_shell.dart`.

**Risk**: low today (nothing currently imports the wrong one), but a
future `import` autocomplete could silently pick the dead file's class
instead of the real one, with no compile error — same package, same
class name, correct-looking import path.

**Effort estimate**: Small (S) — resolved automatically once H1 is
cleaned up; no separate work.

### H3. `lib/l10n_disabled/` — stray, out-of-sync duplicate locale files

Contains only `app_localizations_ar.dart` and `app_localizations_ko.dart`
— duplicates of two of the real, wired locales in `lib/l10n/`, already
excluded from static analysis (`analysis_options.yaml:14`) and not
imported anywhere. Out of sync with the real files (which back the
UAT-only `ar`/`ko-KR` locales referenced by `LocaleService.supported`,
distinct from `productionLocales`).

**Risk**: none to runtime behaviour (excluded from analysis, unimported).
Real risk is confusion — a future contributor editing localisation might
find and edit the wrong file, or not realise `ar`/`ko` translations
already exist for real, live, wired locales elsewhere.

**Effort estimate**: Small (S) — delete the directory once confirmed
genuinely superseded (it appears to be, per the working `ar`/`ko-KR`
support already live via `lib/l10n/`).

## Medium

### M1. `TutorCreditService.respond()` is a canned/mock response generator, live in production

`lib/services/tutor_credit_service.dart` (`respond(String input)`,
~lines 53–114) is explicitly doc-commented `Returns a local mock response
for the given input. No network calls.` — it keyword-matches the input
and returns one of a handful of canned strings per category (explain/
hint/steps/mistake/deep/general), selected via
`DateTime.now().microsecond % items.length`. This is the actual
implementation behind the live Tutor screen (`/tutor`), not a test
double.

This matches an already-established, accepted pattern elsewhere in the
app — Allie has "no live/AI implementation anywhere in this app" by
design (see this session's own memory notes on the Allie architecture) —
so this may well be the same deliberate choice for Tutor. Flagged here
because unlike Allie's card-based UI (which never implies a live
back-and-forth), a chat-style Tutor screen more strongly implies a real
conversational AI to an end user.

**Effort estimate to verify (not fix)**: Small (S) — read
`tutor_screen.dart`'s own copy/framing to confirm whether it already
discloses "offline, scripted responses" to the user, or reads as if it's
live AI. If the former, downgrade to Low/no-action; if the latter, this
is a product-transparency decision for you, not an implementation task
for this audit.
